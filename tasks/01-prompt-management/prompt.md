Please finish the prompt management and publishing system so our team can manage the prompts used by the bot from the production portal without deploying application code each time.

There is some prompt management code already, but it needs to become the complete workflow. Build on the existing application and keep the existing calling and script flows working.

The portal needs a list of prompt types with their names and descriptions, an editor that can switch between versions, and a review page showing the changes relative to the published version before publishing. Support friendly names for versions, clear published/version indicators, token highlighting, and useful validation errors. Users should be able to edit an unpublished version in place or save a new version. Once a version has been published, its prompt content must stay immutable, including through direct API calls; editing it means creating another version. Allow previously published versions to be published again for rollback. Avoid offering a meaningless publish action for the currently published version.

Handle the prompt system's different kinds of tokens properly: action tokens, replacement tokens, conditional blocks, shared prompts, JSON keys, and constants. Preserve the contracts used by the bot. Validate registered and required tokens and reject unsupported tokens. Conditional blocks must work with multiline content. Shared prompts must resolve through their own identifiers, not be confused with primary prompt types. Before publishing a shared prompt, show which prompt types use it. Let authorized users add, update, and remove constants with validation. Include a way to duplicate a prompt type and its token associations; connecting a new type to application behavior can remain an engineering task.

Publishing must update the authoritative version and the Azure Table Storage representation used at runtime. The portal, SQL data, table storage, and runtime caches must agree about which version is published. Handle failures and fallback paths explicitly so a missing cache row or storage problem does not silently select the wrong prompt. Keep published content and version metadata consistent when switching versions or rolling back.

Production prompt management should be the source of truth for every environment. Add authenticated endpoints and a client for non-production environments to fetch published prompts, and allow explicit version overrides for local development and automated tests. Overrides must be scoped to the test or call that requested them and must not change the published default for other calls. Existing inline prompt definitions can be used to migrate the current catalog, but normal runtime execution and tests should use the managed prompt system rather than a second hardcoded source of truth. Local startup must not overwrite managed prompts with old seeds. Include a documented way to initialize or refresh local prompt data without contacting production during unit tests.

Make prompt loading suitable for a live call: eagerly load the primary prompt types needed by the call's script and the shared prompts they depend on, and lazily load other types when requested. Keep the cache scoped correctly, support concurrent requests without sharing an EF context unsafely, and cover missing rows, explicit versions, storage fallback, and cancellation. The LiveKit and Twilio call paths and the text/testing paths all need to initialize and use the same prompt system correctly.

Carry this through the models, migrations, repositories, shared services, portal services and endpoints, and React frontend. Follow the repository's tenancy, authorization, DTO, logging, and backward-compatible schema conventions. Add focused automated coverage for editing, validation, publish/rollback, shared prompts, overrides, and runtime loading, plus frontend coverage for the complete editing and publishing flow. Mock external services. Do not run the paid Bot.Prompts test suite or make production calls.

Please implement the complete feature locally, run the checks that are available, and leave a short description of what changed and any validation that could not be completed. There is no need to publish branches or open a PR.
